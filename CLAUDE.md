# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Management system for **WAGY helados** (an ice cream business): a Next.js 16 (App Router) dashboard for staff to manage orders/expenses/pricing, **plus** a WhatsApp bot that takes customer orders conversationally over the Meta WhatsApp Cloud API, extracts structured order data with an LLM, and writes it into the same `pedidos` table the dashboard reads.

Everything is in Spanish (code comments, DB columns, customer-facing messages). Keep new strings in Spanish (rioplatense/Argentine register — "vos", informal) to match.

npm run dev          # dev server (localhost:3000)
npm run build        # production build
npm run lint         # eslint

- **`npm run eval`** ([scripts/prompts.eval.mjs](scripts/prompts.eval.mjs)) drives the **LLM extraction** end-to-end by POSTing cases to `/api/dev/test-ia`. That endpoint (dev-only, blocked when `NODE_ENV==='production'`) reuses the real `buildSystemPrompt` + all `aplicarOperacion*`, so results reflect what the DB would store. Matching is tolerant (literal or RegExp) because the model is non-deterministic; `EVAL_REPEAT` measures flakiness, `EVAL_FILTER` runs a subset, `EVAL_DELAY_MS` paces calls to dodge Groq's free-tier TPM limit (the suite also auto-retries on rate-limit). See the file header in [test-ia/route.ts](src/app/api/dev/test-ia/route.ts) for PowerShell examples.

The safety switch is **`BOT_TEST_MODE=1`** — it makes `postAMeta` ([whatsapp.ts](src/lib/whatsapp.ts)) capture outbound into an in-memory buffer instead of hitting Meta (returning `true` so the `rol='bot'` persistence still runs), **and** it's required for the endpoint to respond at all (double-guarded with `NODE_ENV`); the endpoint also refuses any phone outside the test prefix `BOT_TEST_PREFIX` (default `54000`). Scenarios ([scripts/escenarios-bot.mjs](scripts/escenarios-bot.mjs)) are **guionados** (fixed turns + an `espera` oracle → mechanical `chequeoAutomatico`) or **exploratorios** (a Groq **cliente-agente** improvises from a persona+objetivo). **Two-step by design** (Motor LLM híbrido, since the Team plan has no Anthropic API key): step 1 `npm run probar-bot` writes `informes-bot/corrida-<ts>/transcripts.{json,md}` (no judging); step 2 **Claude Code judges** those transcripts against [scripts/spec-bot.md](scripts/spec-bot.md) and writes `informe.md`, classifying each conversation ✅ bien / ⚠️ a mejorar / ❓ no contemplado. Keep `spec-bot.md` in sync when the bot's contract changes. Both the bot and the cliente-agente burn Groq tokens, so `PROBAR_DELAY_MS` paces turns; `PROBAR_SOLO_GUIONADOS=1` skips the LLM customer, `PROBAR_FILTER` runs a subset.

## The bot pipeline (the important part)

A customer message travels through this path. The two webhook entrypoints and `procesar.ts` are where almost all the complexity lives.

1. **`POST /api/webhook`** ([route.ts](src/app/api/webhook/route.ts)) — Meta delivers messages here. Branches by `message.type`:
   - **`text`**: insert into `mensajes_chat` with `rol='cliente'` (idempotent via unique index on `wa_message_id` — Meta retries surface as Postgres `23505` and are dropped), then schedule a QStash wake-up `+8s` (`DEBOUNCE_SECONDS`). All real work is deferred. The wake-up is **suppressed** (message stored `procesado=true`, no LLM) when a gate says so: human takeover / recent-operator, or the **anti-DoS rate-limit** (see below).
   - **`interactive`** (button click): the intent is encoded in `button_id`, so we **skip QStash and the LLM entirely** — insert with `procesado=true` and run the action inline via `ejecutarBoton`. Instant reply, 0 tokens. Exception: **quick-reply buttons** (`RESPUESTAS_RAPIDAS`: `resp_pago_efectivo`/`resp_pago_transferencia`/`resp_retira`, sent when exactly one datum is missing) carry no `pedidoId` — the click is mapped to its canonical text ("efectivo", "paso a retirar") and goes through the normal text pipeline, which knows how to merge it into the order being built. **One click per button round** (`pedidos.esperando_respuesta_boton`, migration [20260714120300](supabase/migrations/20260714120300_esperando_respuesta_boton.sql)): WhatsApp leaves both buttons of a pair tappable forever and clicks run inline (no debounce/claim), so a customer could tap *both* (Confirmar+Modificar, Sí+No) and fire two `ejecutarBoton` in parallel — two replies, the second contradictory (`modificarBorrador` has no DB state to guard against a concurrent confirm). Every send of a confirm/modify or cancel button set arms the flag `true` (`enviarResumenYPedirConfirmacion`, `enviarConfirmacionCancelacion`, the greeting re-offer in [procesar.ts](src/lib/bot/procesar.ts), the `/api/gestionar-borradores` reminder); `ejecutarBoton` **consumes it atomically** (`UPDATE … SET esperando_respuesta_boton=false WHERE esperando_respuesta_boton=true RETURNING`) before acting — only the first click of the round wins, the rest exit silently. A new send re-arms it, so the customer can always answer the current round. Quick-reply buttons don't need this (already debounced via the text pipeline).
   - **media** (`image`/`video`/`document`/`sticker`): the bot can't resolve these, but staff need to see them. Download + store and flag for human attention — see **"Media entrante + aviso de intervención humana"** below. Inserted `procesado=true` (never reaches the LLM).
   - **`audio`** (voice notes): the exception to "media never reaches the LLM". After download+store, the bot **transcribes it with Groq Whisper and feeds the transcript through the normal text pipeline**, as if the customer had typed it — see the audio branch in **"Media entrante + aviso de intervención humana"** below. Inserted `procesado=false` (so the atomic claim picks it up), unless the transcription fails/comes back empty, in which case it falls back to the human-delegation path like any other media.
   - **`location`**: stored like media (`media_lat`/`media_lng`), but instead of flagging a human the bot asks for the written address (a pin is almost always the delivery address) — the normal text flow takes it from there.
   - **anything else** (`contacts`, …): reply "solo leo texto" and do nothing else (don't insert, don't schedule).
2. **`POST /api/procesar-pendientes`** ([route.ts](src/app/api/procesar-pendientes/route.ts)) — QStash calls this 8s later. Protected by `verifySignatureAppRouter` (QStash signing keys). Just delegates to `procesarMensajesDeCliente`. Returns 500 on error on purpose so QStash retries.
3. **`procesarMensajesDeCliente`** ([procesar.ts](src/lib/bot/procesar.ts)) — the core. See below.

### Debounce + atomic claim (why messages aren't double-processed)

Each incoming message schedules its **own** wake-up. The system relies on two mechanisms together:
- **Defer**: if the newest unprocessed message is younger than `DEFER_THRESHOLD_MS` (5s, intentionally `< 8s` debounce), the worker assumes the customer is still typing and bails — a later wake-up will catch the whole batch once there's silence.
- **Atomic claim**: `UPDATE ... SET procesado=true WHERE procesado=false AND rol='cliente' RETURNING ...`. The first wake-up to fire claims all pending rows; concurrent/later wake-ups get 0 rows and exit. This is what prevents two workers from each answering a subset of a split message. (The `rol='cliente'` filter is defensive — bot rows are already `procesado=true` — so the bot's own persisted replies can never be claimed as input.)

Right after a successful claim, `marcarLeidoYEscribiendo` marks the newest claimed message as read (blue ticks) and shows the **typing indicator**. It runs **post-claim, not in the webhook, on purpose**: showing "escribiendo…" during the debounce makes customers stop typing mid-batch to wait for the reply.

### Rate-limit anti-DoS (webhook)

A single phone flooding the bot would burn the shared Groq token budget (200k TPD per model), so `manejarTexto` gates on volume **before scheduling the wake-up** ([rate-limit.ts](src/lib/bot/rate-limit.ts)). `estaRateLimiteado` counts this phone's `rol='cliente'` rows in a **rolling window** (`RATE_LIMIT_VENTANA_MS`, 1h); if it reaches `RATE_LIMIT_MAX` (40) the message is stored `procesado=true` (visible to staff, invisible to the claim/defer), **no wake-up is scheduled** (0 tokens), and `marcarRequiereAtencion` fires so the header conversations menu lights up. The bot **does not reply** — answering a flood just amplifies the DoS.

- **Window is intentionally long (messages/hour), not burst**: the debounce + atomic claim already collapse a rapid burst into a single batch = one LLM call, so bursts are already cheap. The real vector is a *sustained* trickle (one message every few seconds for a long time), each triggering its own batch. A real order uses ~10-15 messages total, so 40/h is comfortably above legit use.
- **Not a permanent block — self-healing.** It's a rolling count, not a ban: once the phone drops below 40 messages in the trailing hour (i.e. slows down or stops), the very next message schedules the bot normally again. `requiere_atencion` (the staff signal) and the rate-limit (the count) are **independent** — clearing the flag by opening/replying doesn't change the count, and the count expiring doesn't touch the flag.
- **Fail-OPEN** if the count query errors (unlike the fail-closed auth gates): we'd rather serve a real customer than block them over an internal glitch; the token risk is bounded, a lost legit order isn't.
- Only applies when there's **no** active human takeover / recent operator (those already stop the LLM on their own). Pure helper `superaRateLimit` (tested); threshold/window are tunable constants.
- **Manual reset** (`resetearRateLimit` → the chat modal's "Resetear límite"): for a *legit* customer who tripped the limit, staff don't have to wait out the hour. It stamps `atencion_humana.rate_limit_reset_at = now()`; `estaRateLimiteado` counts only from `max(window start, reset watermark)` (pure `calcularDesdeRateLimitMs`, tested), so the count drops to ~0 and the phone is served immediately.

### Manual block (webhook, all message types)

Separate from the automatic rate-limit: staff can **hard-block** a phone from the chat modal ("Bloquear"/"Desbloquear" → `bloquearNumero`/`desbloquearNumero`, persisted in `atencion_humana.bloqueado`; migration [20260721120000](supabase/migrations/20260721120000_bloqueo_manual_y_reset_rate_limit.sql)). While blocked, `POST /api/webhook` checks `estaBloqueado` **before branching by type** and routes to `manejarBloqueado`: the message is stored `procesado=true` (a minimal row, no media download) so the number stays visible/reachable in the conversations menu, but **nothing else runs** — 0 tokens, no reply, no human ping, any message type. The block affects **only the bot**; the operator can still send manual messages. `estaBloqueado` is **fail-open** (read error / column not yet migrated → not blocked), same philosophy as the rest of `atencion-humana.ts`. A blocked number stays un-blockable even when dormant: the **`/conversaciones` "Bloqueadas" tab** lists all `bloqueado=true` phones straight from `atencion_humana` with no time window, so one that went silent still shows and can be un-blocked (see "Inbox de conversaciones" below — this closed the former limit where a dormant blocked number dropped off the 24h menu with no UI to reach it).

### LLM extraction

- Model: **Groq `openai/gpt-oss-20b`** via the Vercel AI SDK `generateObject` with a **Zod schema** (`PedidoIASchema`), `temperature: 0`. Validation failures are retried manually up to 3× (the SDK marks them non-retryable, but they're really model non-determinism, e.g. returning `"false"` as a string).
- **Model fallback on quota exhaustion**: the extraction loop walks an ordered chain `MODELOS_EXTRACCION` = `gpt-oss-20b` (primary) → `gpt-oss-120b` → `moonshotai/kimi-k2-instruct`. On a **429** (`esRateLimit`, tested — `statusCode===429` or a rate-limit/TPD message) the loop **advances to the next model** (each has its own separate TPD bucket on Groq) instead of leaving the customer with "no te entendí"; on a validation error it retries the **same** model up to `MAX_ATTEMPTS` and then gives up (fallback is for *quota*, not bad parse luck). This lives **only in production** (`procesar.ts`): the nightly harness and `/api/dev/test-ia` stay hardcoded on `gpt-oss-20b` on purpose — a 429 there must surface, not be masked, since the point is to test the real model. All chain models support structured output. **Fallback alert**: each 429 hop is recorded to the `alertas_modelo` table (`registrarAlertaFallback` in [alertas.ts](src/lib/bot/alertas.ts), fire-and-forget + fail-open — an ops-telemetry write must never block or break the already-degraded customer reply) with `modelo_agotado` + `modelo_fallback` (the pure `siguienteModelo`, tested — `null` when the whole chain is exhausted, the worst case). The dashboard surfaces it live: the **`AlertaModelo` banner** ([alerta-modelo.tsx](src/components/ui/alerta-modelo.tsx)) is mounted inside the `Header` (so it shows on every page), loads unresolved alerts from the last 24h via the `getAlertasModeloActivas` server action and stays live over Realtime, and a "marcar visto" dismiss calls `resolverAlertasModelo` (both in [actions/alertas-modelo.ts](src/lib/actions/alertas-modelo.ts), service-role behind an auth check). Without this, a quietly-exhausted primary was invisible (only `console.warn`) until the fallback also ran out and customers started getting "no te entendí". Migration [20260722120000](supabase/migrations/20260722120000_alertas_modelo.sql) creates the table (RLS select for `authenticated` + `supabase_realtime` publication). The table isn't in `src/types/supabase.ts` yet, so both the bot helper and the action use an **untyped** service-role client on purpose (same call as [atencion-humana.ts](src/lib/bot/atencion-humana.ts) — no `update-types` needed to compile).
- **The model extracts a literal + an operation; TS does the merge.** This pattern is used for three fields, so the model never has to echo back a full merged value (which is where it used to drop/mangle data):
  - **Quantities**: `cantidad_*` (literal) + `cantidad_*_operacion` (`sumar`/`restar`/`reemplazar`/`mantener`) → `aplicarOperacionCantidad` against the current qty. The model never does arithmetic — *except* it sums a single-type flavor breakdown ("los de agua 20 de X y 40 de Y" → 60), the one allowed sum.
  - **Aclaración** (address detail): `aclaracion` (literal of *this* message) + `aclaracion_operacion` (`agregar`/`reemplazar`/`mantener`) → `aplicarOperacionAclaracion`. `agregar` sends only the new fragment and TS concatenates, so the existing text can't be lost.
  - **Observaciones** (flavors): see the slots note below — `obs_agua`/`obs_crema`/`obs_general` + per-slot operations.
  - `datos_completos` is also computed in TS, not by the model.
- **`intencion`** is a single enum (`cancelar`/`confirmar`/`confirmar_cancelacion`/`rechazar_cancelacion`/`saludo`/`modificar_sin_datos`/`consultar_precios`/`consulta_negocio`/`datos_pedido`), not a set of booleans. The prompt only shows the intents valid for the current state. Two overrides in `procesarMensajesDeCliente` *reclassify* a model `saludo`/`modificar_sin_datos` to `datos_pedido` when the raw output actually carried changes.
- **`consulta_negocio` = answer-from-context, then delegate**: a business question is **first answered by the bot itself** when it has the info, and delegated to a human only when it doesn't. The answering is a **grounded free-text step** ([consultas-negocio.ts](src/lib/bot/consultas-negocio.ts)) — the deterministic model classifies the intent as always, but for a business question `procesarMensajesDeCliente` calls `intentarRespuestaNegocio`, which builds a **curated context block** (`construirContextoNegocio`, pure) from the known constants (agua/crema types, `SABORES`, `ENTREGA` demora, `ENVIOS`, `PAGO_TRANSFERENCIA`), the active price list, **and the active order's own data including `precio_total`** (so "¿cuánto es mi total?" is answerable), and asks a **separate LLM call** (`responderConsultaNegocio`, own tiny schema `{puede_responder, respuesta}`, `temperature 0`, own `MODELOS_CONSULTA` 429-fallback chain, 12s timeout) to reply in 1-2 sentences *using only that context*. If `puede_responder` → the bot sends the brief answer, **no** `requiere_atencion`. If not (hours, specific delivery zones, day-of stock, promos, wholesale, complaints, invoicing — the "LO QUE NO SABÉS" block anchors this) → **fail-safe to human delegation** exactly as before: `marcarRequiereAtencion` (amber dot + badge) + a "te contesta una persona" reply. This is the consigna's design — instead of a state per possible question, give the model *bounded* context and a `puede_responder=false` escape hatch, so it answers what it knows and never hallucinates the rest. Any error/timeout/exhaustion in the grounded call also fails safe to delegation. The real-vs-noise filter still lives **in the prompt**: off-topic ("quién ganó el partido?") and nonsense fall to `datos_pedido`. The delegation text **rotates** (`elegirTextoDelegacion`, seeded) and switches to a "ya avisé" variant when `requiereAtencionActual` shows a pending flag, so repeated insistence isn't answered word-for-word identically (was a robotic loop). **Mixed message (order data *and* a real question)**: handled by an **orthogonal schema field `pregunta_negocio`** (string|null) that the model fills *whenever* there's a real business question, independently of the single `intencion` enum. When `pregunta_negocio` is set and the primary intent isn't the pure `consulta_negocio` (which has its own early-return handler), `procesarMensajesDeCliente` **answers-or-delegates** the question up front and then **lets the order flow continue** — so the pedido is still built/updated (summary or ask-for-missing) *and* the question is resolved (this is what killed the old "negar y después contestar" contradiction: the bot now answers the price/change itself instead of pinging a human then showing the total in the next bubble). This replaced the old known limit where a mixed question was silently dropped (and, when the order text was un-parseable like "porción con 2 bolas", the customer got nothing at all). Cost of the "always delegate" design: a false-positive `pregunta_negocio` on a normal order pings a human unnecessarily — the prompt is strict that bromas/off-topic/nonsense are NOT business questions. Defensively, `esPreguntaNegocioReal` treats the model's stringified `"null"`/`"none"`/`"undefined"`/empty (a known non-determinism, same as the `"false"` string) as *no question* — otherwise the literal text `"null"` would trip a phantom delegation. The same guard applies to payment: `normalizarMetodoPago` coerces the model output to exactly `'efectivo' | 'transferencia' | null`, so a stringified `"null"` can't slip through as a valid payment (`Pago: null` in the summary).
- **Address sanity check (`pareceDireccion`)**: a deterministic TS guard backs up — doesn't replace — the model's address judgment. It requires a street name (≥3-letter word that isn't a unit keyword like "depto"/"piso") **and** a number; `"retira"` passes as a sentinel. If the model put a non-address (an aclaración like "depto 6", or a street with no number) into `direccion`, it's nulled. This runs **before** the greeting override (so junk doesn't count as "useful data") and **before** the historical-address injection (so a known-good saved address fills in instead).
- **Pickup net (`mencionaRetiro`)**: a second deterministic guard for the pickup sentinel. If after `pareceDireccion` no valid delivery address remains but the raw customer text says they'll pick up (any conjugation/variant: "retiro", "paso a retirar", "lo paso a buscar", "lo busco", "paso por el local"), `direccion` is set to `"retira"`. It runs **after** `pareceDireccion` (so an ambiguous "Corrientes 1234, retiro" keeps the real street) and **before** the historical-address injection (a pickup must not be back-filled with the saved address). This is what makes "paso a retirar" inline in the first turn work even when the model doesn't emit the sentinel.
- **Short-circuit**: before calling the LLM, `intentarShortCircuit` handles unambiguous single messages given the state ("sí" in `esperando_cancelacion`, "hola" with an active order) heuristically — tolerant of typos/accents/emoji/stretched vowels. Saves latency, cost and model errors on trivial cases. It runs only when the batch is one message and never on ambiguous input. The match is **whole-message exact** against the normalized form, using the literal sets `CONFIRMACIONES`/`NEGACIONES`/`SALUDOS`. These sets are an *optimization*, not the brain — anything not in them falls through to the LLM, which generalizes. To grow them from real usage, `npm run minar` ([minar-expresiones.mjs](scripts/minar-expresiones.mjs) → dev endpoint `/api/dev/minar-expresiones`) surfaces frequent short customer messages that currently miss the sets; additions are **human-reviewed** (a bad entry in `CONFIRMACIONES` would auto-confirm orders the customer is rejecting, with no LLM safety net).
- The system prompt is built by **`buildSystemPrompt(pedidoActivo)`** and branches on order state: a "modification/extraction API" prompt when there's an active order (`borrador`/`pendiente`/`esperando_cancelacion`), vs. a "new order from scratch" prompt otherwise.

### Observaciones: keyed slots (flavors per ice-cream type)

`observaciones` is **not flat** — it's structured by type ("los de agua …", "los de crema …", plus type-agnostic notes). To let TS own the keyed merge (replace the agua segment, keep the crema one) without re-parsing free text:

- The DB has a `observaciones_detalle` **jsonb** column = `{ agua, crema, general }`. This is the **bot's internal source of truth**.
- `observaciones` (text) is the **projection** TS regenerates from the slots via `reconstruirObservaciones` on every bot write. It's what the kitchen, dashboard and customer summary read — **humans only ever see/edit the flat text**, never the slots.
- The model fills the slot(s) it's changing (`obs_agua`/`obs_crema`/`obs_general` + per-slot `reemplazar`/`agregar`/`mantener`/`limpiar`); `aplicarOperacionObs` applies each and `leerSlots` reads the current ones.
- **Manual dashboard edits collapse the slots**: `actualizarPedidoCompleto` sets `observaciones_detalle = null`. On the next bot turn, `leerSlots` re-seeds `general` from the flat text — so the bot loses per-type granularity for that order until the customer restates by type, but **never loses data**. Same fallback covers pre-migration rows.

### Bot responses are persisted too (so the LLM sees its own last turn)

Every successful send via `enviarMensajeWhatsApp` / `enviarMensajeConBotones` ([whatsapp.ts](src/lib/whatsapp.ts)) inserts a `mensajes_chat` row with `rol='bot'` and **`procesado=true`**. The `procesado=true` is what keeps these rows invisible to the atomic claim and the defer (both filter `procesado=false`), so persisting a bot reply mid-batch can't trigger phantom wake-ups or be claimed as input. The worker feeds the bot's last turn into the prompt so a bare "dale" after "¿confirmás?" is classified with context. Button messages persist the body + `[opciones: …]` so the model sees what choices were offered. Persistence runs **only on a successful send** — a send that failed never leaves a row claiming the bot said something the customer never got.

Both send helpers go through `postAMeta`, which adds an 8s per-attempt timeout (shorter than undici's 10s connect timeout) and **retries up to 3× on connection failure / timeout / 5xx**, but not on 4xx (our bad request — token, payload). This makes transient blips toward Meta self-heal.

For **longer Meta outages** (beyond the retry budget, where QStash won't retry because the consumer already returned 200), the **confirmation summary** has a re-send safety net: `enviarResumenYPedirConfirmacion` sets `pedidos.resumen_pendiente=true` when the send fails (and clears it on success). A pg_cron job (every ~2 min, via `pg_net`) hits **`/api/reenviar-resumenes`** ([route.ts](src/app/api/reenviar-resumenes/route.ts), auth `Authorization: Bearer CRON_SECRET`), which re-sends summaries for `borrador` orders flagged pending within a 2h window (the window bounds retries without a counter; stale drafts get auto-rejected at 6h by `/api/gestionar-borradores`). Only the **summary** is covered — it's reconstructable from the `pedidos` row; arbitrary bot text replies still aren't, and a lost one is still lost silently.

### Toma humana (chat manual desde el dashboard)

The dashboard has a **chat UI** where staff can message the customer manually over the same WhatsApp number and read replies live (Supabase Realtime on `mensajes_chat`, filtered by `telefono`). The whole chat body (history + Realtime + send + moderation bar + active-order panel) lives in **`ChatPanel`** ([chat-panel.tsx](src/components/pedidos/chat-panel.tsx)), a layout-flexible component (`flex-col`, message list `flex-1`) rendered two ways: wrapped in a Dialog by **`ChatModal`** ([chat-modal.tsx](src/components/pedidos/chat-modal.tsx), a thin wrapper), and inline in the right pane of `/conversaciones` (see "Inbox de conversaciones"). It's **keyed by `telefono`, not by order** (props `{ telefono, pedidoId?, activo?, onVolver? }`): the modal opens from a row's dropdown (`pedidoId` set) **or** from the header conversations menu for a customer with no order (`pedidoId` omitted). `activo=false` stops the panel from loading/subscribing when logically hidden. On open it hydrates its whole state in **one** server round-trip via `getDatosChat(telefono)` ([actions/mensajes.ts](src/lib/actions/mensajes.ts)) — one auth check + a parallel read of the newest history page (`traerHistorialPagina`, `PAGINA_HISTORIAL`=50), takeover state, active order, and block flag — instead of the four separate actions (each re-validating the session) it used before. **History is paginated** (cursor by `created_at`): the panel loads 50 messages and fetches older batches via `getMensajesAntiguos(telefono, antesDeISO)` when the operator scrolls near the top, prepending them while preserving scroll position (a `useLayoutEffect` restores the offset so the view doesn't jump; a `hayMas` flag stops paging when a partial page comes back). Replaced the old fixed 500-message load. **Scroll to bottom**: the panel tracks `pegadoAlFondo` (updated in `onScroll` by distance-to-end, threshold 40px) and, while true, sticks the view to the bottom whenever the content grows — via `useLayoutEffect` on `mensajes` **and** a `ResizeObserver` on the list container that fires when late-loading images/videos change the height. This fixes the old bug where the chat opened halfway through the conversation because the initial `scrollIntoView` ran before images resolved. When `pegadoAlFondo` is false a **floating "bajar al fondo" button** appears at the bottom-left; clicking it snaps to the end and re-pegs. **Day separators (WhatsApp-style)** are injected between messages when the local day changes (pure `mismoDia`), labeled by pure `etiquetaFecha` ([fecha-chat.ts](src/lib/fecha-chat.ts), tested): "Hoy" / "Ayer" / "19 de julio" / "19 de julio de 2024" (año solo si difiere del actual). Sending goes through `enviarMensajeManual` ([whatsapp.ts](src/lib/whatsapp.ts)) — same `postAMeta` as the bot, but persisted with **`rol='operador'`** so the UI distinguishes human replies from bot ones (the atomic claim only filters `rol='cliente'`, so `operador`/`bot` rows are never claimed as input).

When an operator sends a manual message, the bot is **paused for that customer** (human takeover): `atencion_humana` (a table keyed by `telefono`, helpers in [atencion-humana.ts](src/lib/bot/atencion-humana.ts)) is flagged `activa=true`. While active:
- **Webhook gate** (`manejarTexto`): incoming customer texts are stored with `procesado=true` (visible in the chat + Realtime, invisible to the claim/defer) and **no QStash wake-up is scheduled** → the LLM never runs. 0 tokens.
- **Defensive gate** at the top of `procesarMensajesDeCliente`: if a wake-up was already scheduled before the takeover started, it claims the pending rows and returns without answering.

There's also a **message-based gate** (`intervencionHumanaReciente`, safety net for the flag-based takeover): if the customer's conversation has a `rol='operador'` message (not `descartado`) newer than `VENTANA_MENSAJE_OPERADOR_MS` (6h), the bot stays silent **even when no takeover is active** — the message itself is evidence a human is in the conversation (covers e.g. a failed `activarAtencionHumana` upsert). Instead of replying, the system flags `requiere_atencion` so the operator sees the customer wrote. The **exception is an explicit "Devolver al bot"**: an `atencion_humana` row with `activa=false` and `updated_at` *after* the operator's last message means the human handed the conversation back, and the bot answers normally. The pure decision lives in `debeSilenciarBotPorOperador` ([atencion-humana.ts](src/lib/bot/atencion-humana.ts), tested in [atencion-humana.test.ts](src/lib/bot/atencion-humana.test.ts)); it's checked in the webhook (`manejarTexto`, and the media/location paths suppress their auto-replies too) and defensively in `procesarMensajesDeCliente`.

`ChatPanel` also has an **order panel** (edit + hand back to the bot), docked at the **right end of the green header** (info line + buttons; the header `flex-wrap`s it to a second line when narrow, e.g. the modal): it shows the phone's **active order** (`getPedidoActivoChat` — same lookup semantics as the bot's `pedidoActivo`: `borrador`/`pendiente`/`esperando_cancelacion`, `enviado=false`, 12h window), **kept live via Realtime**: a dedicated channel subscribes to `postgres_changes` on `public.pedidos` filtered by `telefono` (any `INSERT`/`UPDATE`/`DELETE` triggers `refrescarPedido`), so a customer who completes the order in real time is reflected in the header without reloading. Requires `pedidos` in the `supabase_realtime` publication (migration [20260723120000](supabase/migrations/20260723120000_realtime_pedidos.sql); RLS `select` for authenticated was already open, so this doesn't widen surface). A **fallback** in the `mensajes_chat` subscription refreshes the panel whenever a `rol='bot'` message arrives — indirect signal that the bot just wrote the order — so the panel stays fresh even before that migration is applied. With an **"Editar"** button (opens the same [edit-order-modal.tsx](src/components/pedidos/edit-order-modal.tsx) the table uses, now supporting `estado='borrador'`) and an **"Enviar resumen"** button (`enviarResumenManualAccion` in [actions/mensajes.ts](src/lib/actions/mensajes.ts)). The use case: the LLM extraction got something wrong, or the order deserves a special price the tier list doesn't know (promos, wholesale) — the operator fixes the data/price in the edit modal and sends the summary, and the rest of the flow goes back to the bot. Sending: guarded UPDATE to `estado='borrador'` (owner phone, intervenible states, never `enviado=true`, completeness — a partial draft's summary would show empty fields), then `enviarResumenYPedirConfirmacion` (arms `esperando_respuesta_boton`, clears/sets `resumen_pendiente` so a failed send is retried by the cron) and `desactivarAtencionHumana` — the explicit hand-back also satisfies the message-based gate, so the bot can answer the customer's button click even though an operator wrote <6h ago. A manual price survives later bot updates because `procesar_pedido_final` only re-derives `monto_total_*` from the price list **when the quantities change**; if the customer then changes quantities, the price reverts to the list (known limit). The button is disabled outside Meta's 24h window and while the order is incomplete.

The takeover ends when the operator clicks **"Devolver al bot"** (`finalizarAtencion`), when the operator sends the summary manually (`enviarResumenManualAccion`), or **auto-expires** after `VENTANA_TOMA_MS` (**8h** of inactivity) — so a forgotten takeover resolves itself without a counter or cron (same time-window idiom as `resumen_pendiente`). **Closing the modal does NOT return to the bot on purpose**: the operator can be mid-conversation about a case the bot can't handle (split payment, "en billetes de cuánto vas a pagar?") and the customer may take minutes to answer; auto-returning on close would leave the bot mute right when the reply arrives. The 8h expiry is measured from the **last activity** on the conversation (customer *or* operator) — the webhook calls `tocarAtencionHumana` on each incoming customer message while takeover is active, otherwise a long back-and-forth from the customer's side alone would expire mid-chat. While the takeover is active and the modal for that phone is closed, incoming customer messages fire a **WhatsApp-styled push toast at the top-right** (green border, sender + two-line message preview, loud WebAudio double-ping) via `NotificacionesEntrantes` mounted in the header — this is *only* for "I'm handling this by hand and the customer replied while I was looking elsewhere". **Bot-to-human delegation is a badge, not a toast**: when the bot sets `atencion_humana.requiere_atencion=true` (a `consulta_negocio`, or a `pregunta_negocio` embedded alongside other intents in a mixed message — both call `marcarRequiereAtencion` in [procesar.ts](src/lib/bot/procesar.ts)), the header's chat icon lights its red badge and the conversation gets the amber dot, live. To make that live the header subscribes to `atencion_humana` changes (not just `mensajes_chat` — the delegating customer message was claimed `procesado=true` and doesn't re-fire the menu's INSERT path); `NotificacionesEntrantes` also listens to `atencion_humana` but only to keep its active-takeover set current (no toast). Requires `atencion_humana` in the `supabase_realtime` publication ([20260720120000_realtime_atencion_humana.sql](supabase/migrations/20260720120000_realtime_atencion_humana.sql)). **Meta's 24h window applies**: free-form manual sends only work within 24h of the customer's last inbound message; outside it Meta returns 4xx, `enviarMensajeManual` returns `false`, and the modal surfaces the error (approved templates would be needed, not implemented). Reading `mensajes_chat` from the browser (history + Realtime) needs an RLS `select` policy for `authenticated` and the table in the `supabase_realtime` publication — both added in [20260630120000_chat_manual.sql](supabase/migrations/20260630120000_chat_manual.sql); the bot uses service-role and bypasses RLS, so it's unaffected.

### Media entrante + aviso de intervención humana

The bot only understands text, but the WhatsApp Business number **can't be opened from a phone**, so the dashboard modal is the only channel — staff must be able to **see** what a customer sends (a photo of an address, an audio, a shared location). So media is received, stored, and surfaced; the bot still never interprets it. Schema in [20260630140000_media_chat.sql](supabase/migrations/20260630140000_media_chat.sql): new `mensajes_chat` columns (`tipo`, `media_path`, `media_mime`, `media_caption`, `media_filename`, `media_lat`, `media_lng`), an `atencion_humana.requiere_atencion` flag, and a **private Storage bucket `whatsapp-media`**.

- **Reception** (`manejarMedia` / `manejarUbicacion` in [webhook/route.ts](src/app/api/webhook/route.ts)): the Cloud API doesn't send the binary in the webhook — it sends a `media_id`. `descargarYGuardarMedia` ([whatsapp.ts](src/lib/whatsapp.ts)) does `GET /{media-id}` → temp URL → downloads with the token → uploads to the bucket (deterministic path `telefono/wa_message_id.ext`, `upsert:true` so Meta retries overwrite rather than duplicate). It **also returns the downloaded bytes** in memory so the audio branch below can transcribe without re-downloading. The download runs **before** the insert so the row already carries `media_path` when Realtime fires (the modal only subscribes to INSERT, not UPDATE). Locations have no `media_id` — they store `media_lat`/`media_lng` + a label in `texto` with `tipo='location'`. Non-audio media rows go in `procesado=true`, so they never reach the claim/defer.
- **Audio = transcripción con Whisper** (the exception to "media never reaches the LLM"): in `manejarMedia`, when `tipo==='audio'`, the bot calls `transcribirAudio` ([whatsapp.ts](src/lib/whatsapp.ts)) with the bytes returned by `descargarYGuardarMedia` (no re-download). It calls **Groq `whisper-large-v3-turbo`** directly over its REST endpoint (not the AI SDK's `experimental_transcribe` — that wrapper doesn't surface per-segment confidence, see below), `language: 'es'` + a domain `prompt` biasing flavor/term recognition, `response_format: 'verbose_json'`, 15s timeout via `AbortController`, reusing `GROQ_API_KEY`. **Whisper hallucination guard**: Whisper is trained to always emit text — on silence, background noise, or non-verbal audio (whistling, music) it fabricates a plausible-sounding phrase instead of returning empty (real case that motivated this: a whistled voice note with background noise transcribed as "Tres de la cara de la tierra, el", which the extraction LLM then dutifully filed as an order observación). `esTranscripcionUtil` (pure, tested: non-empty + has an alphanumeric) only catches total silence/punctuation noise, not this — so `transcribirAudio` also runs `esSegmentoAlucinado`/`filtrarSegmentosConfiables` (pure, tested) over each `verbose_json` segment, using Whisper's own per-segment confidence signals (`no_speech_prob`, `avg_logprob`, `compression_ratio` — the same combo whisper.cpp/faster-whisper use): a segment is dropped when `no_speech_prob>0.6 AND avg_logprob<-1.0` (high-confidence "not speech"; `no_speech_prob` alone isn't enough, it also fires on real-but-quiet/noisy speech) or `compression_ratio>2.4` (repetitive looped text, the other hallucination mode). The transcript returned is the concatenation of only the surviving segments — `null` if none survive. If the (filtered) transcript is useful, the shared helper **`encolarComoEntradaDeCliente`** (extracted from `manejarTexto` so audio and text share the *identical* human-takeover / rate-limit gates and QStash scheduling) inserts a row with `tipo='audio'` + `media_path`/`media_mime` (so the modal keeps the player) **and `texto`=transcript**, `procesado=false` — the atomic claim picks it up and the bot processes the voice note **exactly as if the customer had typed it**, including confirmation summary before anything is finalized, so a mis-transcription is self-correcting. If transcription **fails, comes back empty, or every segment is filtered as low-confidence**, it falls through to the normal media path below (stored `procesado=true`, human delegated). Known limits: WhatsApp voice notes are `audio/ogg;codecs=opus` (Groq supports ogg); transcription adds ~1–3s in the webhook before the 200 to Meta; a Meta webhook retry re-transcribes before hitting the `23505` (rare, a wasted Groq call); the confidence thresholds are a heuristic, not a guarantee — a very short, confidently-mis-transcribed hallucination could still slip through. A **dev-only** endpoint [/api/dev/transcribir-audio](src/app/api/dev/transcribir-audio/route.ts) (blocked in production) transcribes an uploaded audio file to check quality without a real Meta `media_id`.
- **Aviso de intervención humana / no-leído**: `requiere_atencion` is a **dual-purpose flag** — it means "the staff hasn't seen this yet", covering both first-time human handoff and "unread messages" during an active takeover (the amber dot in the inbox / Pendientes tab). After storing a **media**, `avisarSiHaceFaltaHumano` sets `atencion_humana.requiere_atencion=true` ([atencion-humana.ts](src/lib/bot/atencion-humana.ts)); **only if there's no active human takeover** does it also reply to the customer *"Recibí tu mensaje, en un momento te atiende una persona 🙏"* (in a takeover the flag alone is enough — the operator is already there and doesn't need an auto-reply in the middle of their exchange). **Under active takeover**, `manejarTexto`/`manejarUbicacion`/`avisarSiHaceFaltaHumano` all call `marcarRequiereAtencion` on every incoming customer message (in addition to `tocarAtencionHumana`) so the chat gets the "unread" highlight until the operator opens it — otherwise a message during takeover only reached the toast and slipped past the list. The flag is **cleared** when the operator opens the chat (`marcarAtendido`) or replies (`activarAtencionHumana`); `ChatPanel` also re-clears it on every incoming customer message received via Realtime while the chat is open (so the chat you're actively looking at doesn't self-mark as unread). `marcarAtendido` additionally fires a **read receipt to Meta** (fire-and-forget) via `marcarLeidoWhatsapp` (whatsapp.ts) — the `status:'read'` payload for the latest customer `wa_message_id`, no typing indicator (distinct from `marcarLeidoYEscribiendo`: the operator may take minutes to write, or just be reviewing). Meta treats read as cumulative on the thread, so marking the newest is enough for the customer to see blue ticks. **Locations are the exception**: a shared pin is almost always the delivery address, so the bot does NOT flag a human — it stores the row (still visible in the modal) and asks the customer for the written address ("calle y número") so the normal flow picks it up.
- **Display** ([chat-panel.tsx](src/components/pedidos/chat-panel.tsx)): the chat's single-shot loader `getDatosChat` (see "Toma humana") returns the media fields with a **signed URL** (`firmarPath`, 1h) since the bucket is private; `CuerpoMensaje` renders by `tipo` (image/sticker `<img>`, audio `<audio>` **plus the transcript from `texto` shown below the player**, video `<video>`, document download link, location → Google Maps link). Realtime rows arrive with `media_path` but no URL, so the panel calls `firmarMedia(path)` to resolve it.
- **Surfacing in the dashboard**: a 📎 badge on the order row whose `telefono` is pending ([columns.tsx](src/components/pedidos/columns.tsx)), plus the **header conversations menu** ([header.tsx](src/components/ui/header.tsx)). The menu lists **recent conversations** (`getConversacionesRecientes`: distinct `telefono` with activity in the last 24h, recency-ordered), with pending ones highlighted (amber dot) and the icon's red badge = pending count. It reads the **same `conversaciones_inbox` view** as the inbox (dedupe + `requiere_atencion` resolved in SQL, sliced to 24h), so one query replaces the former 500-row scan + JS dedupe + separate `telefonosRequierenAtencion` call; it **falls back** to that older path if the view isn't present (migration unapplied) so the header never breaks. Opening a chat does **not** remove it from the list — it only clears the highlight — so a customer **with no order stays reachable** (this is what the per-order entry point couldn't do). Realtime moves a conversation to the front on any new message and flags it pending on a customer media/location. The page derives the table's pending-`telefono` set from this same list ([page.tsx](src/app/page.tsx)), one query. The menu's footer links to the **full inbox** at `/conversaciones` (below).

### Inbox de conversaciones (`/conversaciones`)

The header dropdown is a 24h quick-access list; the **full inbox** ([conversaciones/page.tsx](src/app/conversaciones/page.tsx) + [conversaciones-inbox.tsx](src/components/conversaciones/conversaciones-inbox.tsx)) is the complete view. It **complements** the dropdown (doesn't replace it — the footer item "Ver todas las conversaciones" navigates here). Server component checks auth + renders the same `Header`; the client component holds filter/search/page state and refetches via the `getInboxConversaciones` action ([actions/conversaciones.ts](src/lib/actions/conversaciones.ts)). **Layout is WhatsApp-Web style**: a two-pane split — the conversation list on the left, the selected chat rendered **inline** on the right via `ChatPanel` (not a modal). The page is `h-screen overflow-hidden` so each pane scrolls internally. Responsive: on `md+` both panes show side by side (empty state on the right when nothing is selected); on mobile the list and the chat swap (selecting shows the chat with a back arrow → `onVolver`). The right pane keys `ChatPanel` on `telefono` so switching conversations remounts it with fresh history/state.
- **Data source**: a SQL **view `conversaciones_inbox`** (migration [20260722130000](supabase/migrations/20260722130000_conversaciones_inbox.sql), `security_invoker`) — `distinct on (telefono)` over the **last 30 days** of `mensajes_chat` (window baked into the view so the date filter uses the index), one row per phone with its latest message + `atencion_humana` flags (`requiere_atencion`, `bloqueado`, and a computed `toma_activa` = active & not past the 8h window) left-joined. The action reads it with service-role (bypasses RLS), builds the one-line preview via the pure `armarPreviewMensaje` ([conversaciones-utils.ts](src/lib/conversaciones-utils.ts), tested — media→label, outbound→"Vos:" prefix, elision), paginates (`.range`, 25/pg, `count:'exact'`), searches by phone (`.ilike`).
- **Filters (tabs)**: *Todas* / *Pendientes* (`requiere_atencion=true`) read the view; ***Bloqueadas* reads `atencion_humana` directly** (`bloqueado=true`, **no time window**) so a blocked number that went silent still shows and can be **unblocked** from here (`desbloquearNumeroAccion`) — this is the "no UI to un-block a dormant number" limit finally closed. Rows select the conversation into the right-hand `ChatPanel`; badges mark toma manual / bloqueado / pending.
- **Liveness**: a single Realtime subscription (INSERT on `mensajes_chat`, `*` on `atencion_humana`) triggers a **debounced refetch** of the current page for order/preview/pagination — the server view stays the source of truth, no hand-reconciliation for those. But the `requiereAtencion` flag is also **reconciled in-place immediately** off the same events (using the shared pure `marcaPendiente` helper in [conversaciones-utils.ts](src/lib/conversaciones-utils.ts), the exact criterion the header dropdown uses), so the amber dot in the inbox flips at the same instant as the one in the header — before the 800ms refetch lands. Background refetches (Realtime, marcar-atendido, unblock) pass `conCount=false` to `getInboxConversaciones` so they **skip the `count:'exact'`** (expensive over the `distinct on` view, and the total rarely changes between messages) and return `total:null`; the client keeps its previous total. The exact count is recomputed only on **navigation** (tab/search/page change), where the result set actually changes. The view isn't in `src/types/supabase.ts`, so the action uses an **untyped** service-role client (same rationale as `atencion-humana.ts`).

**Known limits**: media content isn't interpreted by the bot (no transcription/vision). Search is by phone number only (no message-content full-text) and the inbox window is 30 days (blocked numbers excepted — shown regardless of recency). The header dropdown itself is still 24h + no preview/unread/search (the full inbox covers those). A failed download still stores the row; the modal shows "Archivo no disponible". Storage has no retention/cleanup job.

### Order state machine (`pedidos.estado`)

`borrador` → `pendiente` → `enviado`, with `esperando_cancelacion` and `cancelado` as branches. Roughly:
- **`borrador`**: draft built by the bot; customer must confirm. A draft is now **persisted as soon as the customer gives any real datum**, even if incomplete (**partial draft**) — it's created/updated in [procesar.ts](src/lib/bot/procesar.ts) while gathering, with `''` as the placeholder for the NOT-NULL columns not filled yet (`direccion`/`metodo_pago`; `''` is falsy so the missing-data logic reads it as absent). This is what lets subsequent turns **merge deterministically against the DB** (`aplicarOperacionCantidad` & co.) instead of re-extracting the whole order from the 15-min chat history each turn — the old behavior silently dropped data (e.g. the crema quantity vanished when the customer then sent the payment method, because with no `pedidoActivo` there was nothing to merge against and the LLM re-extraction was lossy). While a partial draft is incomplete the bot keeps asking for the missing datum (`pedirDatosFaltantes`) and **never sends the confirmation summary**; `enviarResumenYPedirConfirmacion` and confirmation (text, button, or the `/api/gestionar-borradores` reminder) are all gated on completeness (`pedidoCompleto` / `.neq('direccion','').neq('metodo_pago','').or('cantidad_agua.gt.0,cantidad_crema.gt.0')`). Partial drafts don't show in the default dashboard view (it filters `["pendiente","enviado"]`) and abandoned ones are cleaned up by the same 6h auto-reject. The "reused your last address" heads-up survives multi-turn drafts via the **`pedidos.direccion_de_historial`** column (set on insert when the address was injected from history, cleared by the update paths when the customer changes the address; `enviarResumenYPedirConfirmacion` ORs it with the per-turn flag, so the notice shows whenever the summary finally goes out, including cron re-sends). **A single active draft per phone is enforced by the DB** (unique partial index `pedidos_un_borrador_por_telefono`, migration [20260714120000](supabase/migrations/20260714120000_unico_borrador_por_telefono.sql)): a draft INSERT hitting `23505` is merged onto the existing draft (`fusionarEnBorradorExistente` — incoming fields win, missing ones are kept) instead of creating a duplicate whose summary buttons could point at the wrong order. Drafts **never auto-confirm**: a pg_cron (pg_net, scheduled manually — see the route header) hits **`/api/gestionar-borradores`** ([route.ts](src/app/api/gestionar-borradores/route.ts), auth `Authorization: Bearer CRON_SECRET`) which (1) after ~20 min of customer silence sends a one-shot "¿Seguís ahí?" reminder with the confirm/modify buttons (`recordatorio_enviado`, re-armed to `false` on every summary send), and (2) after 6h of **customer silence** — measured from their last `mensajes_chat` row, NOT from the draft's `created_at` (a modified `pendiente` goes back to `borrador` keeping its original `created_at`; age-based rejection cancelled it minutes later with the customer mid-conversation) — **auto-rejects** the draft (`estado='cancelado'`, `auto_rechazado=true`), notifies the customer (only if silent <12h — Meta's window blocks older sends anyway) and discards the chat history. Both steps skip phones with unprocessed messages (a QStash wake-up is in flight). The same cron also (0) **rescues orphaned pending messages**: if the QStash publish failed in the webhook, the message would stay `procesado=false` forever (customer unanswered, phone permanently skipped as "in flight") — every tick, phones with `rol='cliente'` `procesado=false` rows older than `BARRIDO_PENDIENTES_MIN` (5 min, well above the 8s debounce) get `procesarMensajesDeCliente` called directly; the defer + atomic claim make this safe against a real wake-up firing concurrently. The old auto-confirm cron/function was dropped in [20260712120000](supabase/migrations/20260712120000_recordatorio_y_auto_rechazo_borradores.sql); the now-vestigial `auto_confirmado` column and its `/api/webhook/notificacion` receiver were removed in [20260713130000](supabase/migrations/20260713130000_drop_auto_confirmado.sql) (also disable the Supabase Database Webhook that pointed at that route).
- **`pendiente`**: confirmed, in the kitchen.
- **`enviado`**: dispatched by the courier. **Terminal for the customer** — cancellation/modification is refused. Note the bot treats an order as dispatched via `estaDespachado` = `estado='enviado' OR enviado=true`, so a `pendiente` order with `enviado=true` (courier message already copied, state not yet flipped) is refused too (see invariant #1 below).
- **`esperando_cancelacion`**: bot asked "are you sure?" and awaits a yes/no. If instead of answering the customer sends **concrete changes** (`datos_pedido` + `hayCambiosReales`), that's treated as an **implicit rejection of the cancellation**: the order goes back to `borrador` with the changes applied and the updated summary is sent (before, those changes were silently dropped and the yes/no re-asked). A **clear "no" mixed with another phrase** ("No, no lo cancelo, dame el total ya") used to derail the model's classification and leave the order **stuck** here — now a deterministic net `mencionaRechazoCancelacion` (pure, tested, same idiom as `mencionaRetiro`) detects the explicit refusal on the raw text and, when the model didn't already classify confirmar/rechazar and there are no real changes, **forces `rechazar_cancelacion`** (which resends the summary — so the "dame el total" is answered by the summary itself). The same net gates the early-returning consulta handlers (`consultar_precios`/`consulta_negocio`) via `rechazoCancelacionExplicito` so a price/business question riding on the refusal can't steal the message before the cancellation block runs. The prompt was also tightened: asking for the total is a *consulta*, not an order change. If the customer simply **never answers**, `/api/gestionar-borradores` **cancels the order after `CANCELACION_SILENCIO_HORAS` (1h) of customer silence** — the cancellation request is honored even unconfirmed, because delivering an order the customer believed cancelled is worse than not delivering one whose last instruction was "cancel". Silence is measured from the customer's last `mensajes_chat` row (the cancel request itself is always a customer message); the customer is notified only within `AVISO_CANCELACION_HORAS`, and the decision is pure (`decidirAccionEsperandoCancelacion` in [borradores.ts](src/lib/bot/borradores.ts), tested). Without this, an unanswered "¿estás seguro?" left the order stuck forever in a state invisible to both the bot (12h `pedidoActivo` window) and the default dashboard view.
- **`cancelado`**: cancelled (by the customer or the cron's auto-reject). **Undo window**: if the customer regrets it right after ("no, quiero el pedido") the bot **reactivates** the order instead of starting from scratch. `procesarMensajesDeCliente` looks up the most recent `cancelado` order and, if it was cancelled **within `VENTANA_REACTIVAR_MS` (30 min, from `updated_at`)**, exposes a new `reactivar` intent in the new-order prompt (gated by `buildSystemPrompt`'s `hayPedidoCanceladoReciente` flag — the prompt only offers it when there's something to reactivate). On `reactivar` the cancelled row is flipped back to `borrador` (guard `.eq('estado','cancelado').neq('enviado',true)`) **keeping all its data** — the summary is re-sent (complete) or the missing datum is asked (partial). This fixes the old "descancelar" gap where a regretted cancellation lost the quantity/payment and rebuilt from zero (only the address survived, via historical injection). The data survives because the cancelled row itself is intact — the chat history was discarded by `marcarHistorialDescartado`, but the reopen reads the row, not the history.

Confirmation messages (`mensajeConfirmacion` in [whatsapp.ts](src/lib/whatsapp.ts)) include an estimated time (delivery vs pickup) and, for `transferencia`, the alias to transfer to — both editable constants (`ENTREGA`, `PAGO_TRANSFERENCIA`) in [precios-publico.ts](src/lib/precios-publico.ts).

### Two invariants that have caused real bugs (don't regress them)

1. **`estado` is the source of truth for the state machine; the `enviado` boolean must stay coherent with it — but "already dispatched?" is `estado='enviado' OR enviado=true`.** Dashboard server actions must mutate state through `patchConEnviadoCoherente(estado)` ([actions/pedidos.ts](src/lib/actions/pedidos.ts)): `estado='enviado'` forces `enviado=true`, `estado='cancelado'` forces `enviado=false`. A stale `enviado=true` on a cancelled order once made the bot wrongly say "your order was dispatched" — but that's now impossible because cancelling forces `enviado=false`. Given that guarantee, the "did it already leave?" check treats **both** signals as dispatch, via the pure `estaDespachado(pedido)` ([procesar.ts](src/lib/bot/procesar.ts), tested): `enviado=true` is set automatically the moment the courier message is copied from the system (copy == "it's out"), the **early, reliable** signal; `estado='enviado'` is flipped manually in the dashboard and often **lags** (sometimes to the next day). **Cancellation wins**: `estaDespachado` short-circuits to `false` when `estado='cancelado'`, even if a stale `enviado=true` lingers — the bot's own cancellations (auto-reject / hung-cancellation in `/api/gestionar-borradores`) don't clear the boolean, so this guard is what stops a cancelled order from re-triggering the old "your order was dispatched" bug. Between the copy and the manual state change there's a window where the order has physically left but `estado` is still `'pendiente'` — treating it as dispatched in that window is what stops the bot from letting a customer cancel/modify an order already on its way. `estaDespachado` is used in `buildSystemPrompt`, the `pedidoActivo`-less dispatch fallback (`ultimoPedidoEnviado`, which now also catches `enviado=true` with `estado='pendiente'`), and the button guards (`.neq('enviado', true)`). **Known limit** of refusing modification on a dispatched order: within the 12h `pedidoActivo` window the bot can't tell "add 10 to what I ordered" from "I want to order again", so a genuinely new order is also bounced until the dispatched one falls out of the window. Note the `pedidoActivo` lookup itself still filters `.eq('enviado', false)` (dispatched orders are routed through the `ultimoPedidoEnviado` fallback, not treated as an editable active order).
2. **Order of overrides in `procesarMensajesDeCliente` matters.** The greeting override and "real changes" check run against the model's **raw** output, and the **historical-address injection runs *after* them**. If you inject the saved address first, a bare "hola" from a known customer ends up with `direccion` set → `trajoDatosUtiles=true` → the legitimate greeting is suppressed. Don't reorder these blocks casually. When that injection fills the address on a **new** order (no active order), the confirmation summary tells the customer it reused their last address so they can correct it (`direccionInyectadaDeHistorial` → a line in `enviarResumenYPedirConfirmacion`).

Every state-changing `UPDATE` in the cancellation/confirmation flows uses a **guard** (`.eq('estado', <expected>)` / `.neq('estado','enviado').neq('enviado',true)`) and checks affected-row count to detect races with the courier or the cron between read and write — if 0 rows, send a contextual fallback instead of assuming success. Button handlers in [botones.ts](src/lib/bot/botones.ts) additionally guard `.eq('telefono', numeroCliente)` (only the owner can act).

**`marcarHistorialDescartado`** is called whenever a conversation closes (confirmed/cancelled). It flags all of a customer's messages `descartado=true` so the next conversation's 15-min history window doesn't re-ingest stale fragments ("sumale 50 de agua" from a prior batch).

### Phone number normalization

Meta sends Argentine numbers as `549…`; we strip the `9` (`549` → `54`) in `normalizarNumero` so it matches what messaging apps display. Store/query the normalized form everywhere.

### Zona horaria (fechas y horarios)

Todo el cálculo y formateo de **calendario** del sistema pasa por [zona-horaria.ts](src/lib/zona-horaria.ts) y se resuelve en la hora de Argentina (`America/Argentina/Buenos_Aires`), **sin importar dónde corra el código**. El motivo: el runtime del servidor (Vercel) es UTC, así que `new Date()` + `getHours/getDate/setHours` calculaban el "día" a medianoche UTC = 21:00 AR — un pedido de las 22:00 AR caía en el día calendario siguiente, y el listado (bordes resueltos en el servidor) y los balances (bordes resueltos en el navegador) podían asignar el mismo pedido a días distintos. El módulo usa `Intl.DateTimeFormat({ timeZone })` (sin dependencias) para obtener el offset real del huso, así que sigue siendo correcto si alguna vez vuelve el horario de verano.

- **Consumidores**: `periodo-utils.ts` (bordes día/semana/mes del listado, corre server-side en [page.tsx](src/app/page.tsx)), `fecha-chat.ts` (separadores "Hoy/Ayer" del chat), `date-range-selector.tsx` + `balances/page.tsx` (rango de balances), `chat-panel.tsx` (`horaCorta`) y `conversaciones-inbox.tsx` (`fechaCorta`). Helpers clave: `inicioDelDiaAR`/`inicioDiaSiguienteAR` (fin exclusivo), `inicioSemanaAR`/`inicioMesAR`, `sumarDiasAR`/`sumarMesesAR`, `claveDiaAR` (comparar "mismo día"), `fechaISOAR`, `formatearFechaAR`/`formatearHoraAR` (es-AR + `timeZone` siempre forzado, `hour12:false`).
- **Lo que NO pasa por acá** (y no hace falta): toda la lógica **relativa** (diffs de ms) ya es inmune al huso — debounce, rate-limit, ventanas de toma humana / reactivación / historial / 12h de pedido activo / 24h de Meta, thresholds de borradores, crons `*/N`, columnas `timestamptz` + `now()`, e intervalos `now() - interval` de las vistas. Son instantes, no calendario.
- **Convención de rangos**: `[desde, hasta)` medio-abierto en todo el sistema. El selector de balances manda `endDate` = 00:00 AR del día **siguiente** al último día; `obtener_balance` (migración [20260724120000](supabase/migrations/20260724120000_balance_borde_medio_abierto.sql)) y `ObtenerGastos` filtran `created_at >= desde AND created_at < hasta`, igual que el listado. Antes el balance era inclusivo-inclusivo (`<=`) y podía doble-contar un pedido en el borde exacto.
- **Tests TZ-deterministas**: [zona-horaria.test.ts](src/lib/zona-horaria.test.ts) y [fecha-chat.test.ts](src/lib/fecha-chat.test.ts) construyen instantes UTC explícitos y afirman el resultado AR, así prueban la invariancia al TZ del runtime (el caso crítico es la franja 21:00–23:59 AR, que en UTC ya es el día siguiente).

## Dashboard side

- Server Components fetch directly from Supabase ([app/page.tsx](src/app/page.tsx) — orders table with URL-param filters; `/balances`). Mutations go through `'use server'` actions in [src/lib/actions/](src/lib/actions/).
- Auth: Supabase SSR. `src/proxy.ts` is the **Next.js 16 middleware** (renamed from `middleware.ts`) — it refreshes the session on every request; unauthenticated users are redirected to `/login` by the page itself.
- Pricing is **quantity-tiered**: `listas_precios` (one `activa`) → `reglas_precios` (per `tipo_producto` `agua`/`crema`, `min_cantidad` threshold → `precio_unitario`). `calcularPreciosUnitarios` ([precio-utils.ts](src/lib/precio-utils.ts)) picks the highest applicable tier. `precio_total` and the `monto_total_*` columns are persisted on the row (the bot's `enviarResumenYPedirConfirmacion` reads `precio_total` straight from the DB — it's filled by DB-side logic/trigger, not by the bot).
- UI: Tailwind v4 + Radix UI + shadcn-style components in [src/components/ui/](src/components/ui/), TanStack Table for the orders grid.

## Supabase clients (pick the right one)

- **Service role** (`@supabase/supabase-js` with `SUPABASE_SERVICE_ROLE_KEY`): used **only server-side in the bot pipeline** (webhook, procesar, botones) to bypass RLS. Never expose this.
- **`@supabase/ssr` server client** ([supabase-server.ts](src/lib/supabase-server.ts)): Server Components / server actions, scoped to the user's cookies/session.
- **Browser client** ([supabase-client.ts](src/lib/supabase-client.ts)): client components.
